# ウレナビ完成設計・実装順序（2026-10-16）
## 価値の定義
iPhone上で「商品を見つける→比較する→事実を確かめる→購入理由が伝わるROOM投稿文を用意する→本人が投稿を確認する→交流・成果を記録し次の行動を決める」を最小操作で完了する単一アプリ。単なる文章生成器にしない。検索は無料・検証済み投稿文生成は有料という商品設計。通常版/Pro版の分割は行わない。販売価格1,480円/月は目標であって採算・継続価値が確認されるまで確定しない。

## 不変条件（コード修正時の保護境界）
- 商品根拠: 楽天の許諾ある取得経路だけを用い、出典・取得日時・不明情報を明示。スクレイピング/サーバーによる無許可取得は禁止。
- 投稿文: 原文引用に紐づく品名/対象/作用/条件/否定/数量/ブランドだけを採用。推測メリット・誇大・断定・単語のみ・仕様の羅列を完成にしない。
- 既存の product{what,acts_on,acts_on_quote}, sentences[{text,kinds,quotes}] と機械拒否・AI全文章検証を変えない。unclear拒否。誤記、商品取り違え、ブランド逆転、部分引用も拒否。
- 生成判断: ①検証済み再利用 ②根拠のあるローカル生成 ③不足時のみ無料Groq。429時は止め、再試行は本人操作だけ。検索の残りも停止。
- 公開: 未検証文はコピー不可。生成中/保留/失敗/完了の状態がUI・台帳・コピーで一致すること。
- iPhone: 検索/投稿文/交流/成果/今日の作業をタブで分離。楽天商品ページへの遷移は商品リンクのみ、次商品操作を偽装しない。
- main/Production/決済、PR159/162のmerge・Draft解除は証拠と許可が揃うまで行わない。

## 単一の情報経路
商品ID+商品名+引用元の事実+取得時刻 → 同一商品判定と候補比較 → 事実抽出 → 購入理由候補の生成 → 出典と意味の照合 → 最終検証 → validated copy → コピー → ユーザー投稿確認 → 台帳/成果。
検証可能な商品の事実と「使う場面の提案」を区別する。使用場面は一般的な用途として適合しても、性能や結果を保証するように言い換えない。
出力における媒体差は整形だけとし、媒体ごとに未検証事実の生成ルートを持たない。

## 受入順序・証拠
0. 開発版の現HEAD、GitHub両CI、Vercel Preview、Productionを照合する。失敗は実機/コード/テストフィクスチャ/外部制約に分類。
1. CI契約整合: 古いソース文字列の検査を振る舞いテストに置換。ただしテストの削除・合格条件の緩和は禁止。テスト側のmockは実装の正規経路と一致させる。
2. 品質横断: 780商品で完成扱いになった全件のコピーに引用・対象・否定・保証の誤りが無いこと。拒否率も集計し、根拠のある商品が不当に落ちる原因を説明する。洗濯ネット等の実例は回帰として加えるが商品名ベタ書き分岐はしない。
3. Preview: npm run vercel-build、Verify Urenavi、ROOM Copy Regressionの成功と同SHAのPreview READY・HTTP200を必須にする。
4. 機能: 検索→候補比較→最大3商品生成→待機/429停止→本人再開→コピー→ROOMリンク→本人投稿確認→重複除外→交流記録→成果入力→復元を実環境で一周する。連打/検索切替/戻る/再読込も検証。
5. 安全性: 未検証コピー禁止、認証失効、ユーザー切替、手動操作、データ保存/復元の整合性、個人別データ隔離を検証。
6. 無料Groq/経済性: 現在の無料枠の実通信件数、入力/出力トークン、429、月間想定コスト、商用ホスト費、決済手数料を計測。不明なら採算未確定。
7. 法務・販売: 楽天の商用利用書面回答とデータ使用許諾、商用ホスティング条件、5名の無料テスターの実作業と購入意欲の検証が揃うまで一般発売と課金を開始しない。

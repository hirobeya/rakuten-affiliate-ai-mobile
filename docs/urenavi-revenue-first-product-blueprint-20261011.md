# 超絶スーパーウルトラウレナビ改｜売上起点の確定設計案（2026-10-11）

## 北極星
楽天ROOM運営者の売上獲得を支援し、購入者が「料金を払って良かった」と判断できる商品にする。売上そのものは保証しない。商品発見・選定・文章作成・投稿準備・成果分析を一つの流れにし、iPhoneだけで完結する。

## 不変条件
- 商品の事実から購入メリットを表現。根拠のない断定、対象や条件の意味拡張、架空の効果・売上予測は禁止。
- 既定のproduct(what/acts_on/acts_on_quote)+sentences(text/kinds/quotes)生成・機械拒否・全文AI検証契約を統一する。
- Groqはローカルの安全な判定と検証済み再利用では処理できない場合に限定。429時は停止・自動再試行なし。
- iPhone中心。ユーザーによる30件の手入力、コピー&ペーストの反復など、作業負荷を増やす方式を主機能にしない。
- 楽天APIを有料機能で使用する前提は置かない。楽天の利用規約、データ取得・自動操作の可否、商用ホストの条件はリリースゲートにする。無許可スクレイピングはしない。
- main・Production・決済はユーザーの承認なく変更しない。PR #159と#162はDraft・未merge。

## 顧客のジョブと価値
1. 今日何を投稿すればよいかを迷わず判断したい → 根拠付き商品候補と選定理由。
2. 商品の特徴と購入メリットを伝えたい → 裏付けのあるコピー・拒否理由。
3. 毎日の運用を楽にしたい → 候補から投稿準備まで一続きの操作、重複防止。
4. 売上を改善したい → 取得可能な実績に限った振り返りと次の改善提案。

## 製品構成
- 通常版：検索・商品理解・検証済みメリット訴求・1商品の投稿準備。
- Pro：候補取得アダプタ→選定評価→共通の商品理解・文章エンジン→複数商品の投稿準備→重複/履歴→計測と改善提案。
- 機能別の別AI生成器を作らず、通常版とProを同一の品質判定に接続する。

## 技術フロー
候補源（規約適合・利用許可・取得元表示必須）
→正規化（商品名、価格、素材、用途、数値の出典、取得時刻、条件）
→商品同一性・重複判定
→評価（検索/需要一致、ユーザー用途、価格の妥当性、レビュー信頼度、季節性、料率:各欠損はnull）
→順位と選定理由（推測値と実績を区別）
→V3商品理解・根拠付き文章生成・検証
→readyのみ投稿準備（blockedは配信せず原因を記録）
→実行可能な投稿支援（無許可の自動投稿/自動いいね/自動フォローは実行しない）
→実績データを取得できる範囲で記録・分析→次の選定に反映。

## 既存コードの再利用と是正対象
- api/room-ai-v3.js、lib/super-urenavi-v3-copy.js：通常版の共通文章エンジン候補。確定生成スキーマとの不一致を解消するまで完成扱いしない。
- lib/pro-search.js：score70/30は独自ヒューリスティック。売上予測ではない。API交通と候補評価は分離済みだが、有料版の検索経路には楽天API依存が残る。
- api/pro.js：候補キューと設定保存は存在するが、投稿予定時刻は実行エンジンでない。
- public/app.html：Pro→通常版への引継ぎはあるが、商品の文章完成までの一括実行は未検証。
- フォロー/いいね：現状チェックリストであり、自動化と呼ばない。
- 実績：投稿別にどの情報を取得/連携できるか確認する。未取得値を成果予測として見せない。

## 実装順序と出口基準
Gate A 基盤: 商品理解・文章生成・検証の単一契約を実装し、既存回帰に加えて商品カテゴリ横断/未見商品/否定/条件/単位/危険なクレームを実通信含め検証。失敗例の根本原因を特定してから修正。
Gate B Pro経路: 候補取得の合法なデータ源を確保。候補→選定根拠→共通エンジン→投稿準備を連続操作で完成。キーワード/候補の混線ゼロ、誤選定時の安全停止。
Gate C 運用: 投稿/重複管理・実際に許される操作のみを実装。時刻設定だけを「予約投稿」と呼ばない。
Gate D 成果: 分析可能なデータ源を確認し、実際の売上/報酬を推測値と区別。作業時間、利用継続、文章採用率、売上への貢献を少人数の利用者テストで確認。
Gate 0 商用の条件: 楽天規約/商用ホスト/AI予算/決済要件を満たさなければ販売開始不可。

# ウレナビ｜文章品質の停滞原因と採用判断（2026-11-13）

## 判断の根拠

オーナーの明示評価：
- PR #170 実文は「前よりはまし」
- ただし「② 自然にはなったけど、商品を欲しいと思うほどではない」
- これ以上ルールを追加し続けると壊れる、という懸念

確認した実装：
- PR #169 `grounded-local-recovery.js`: 原文から一部の特徴を抽出し、いくつかの定型関係で文章候補を組む。楽天商品4件で候補取得。ただし公開認証はなし。
- PR #170 `narrative-editorial.js`: 特徴から始める構成だが、relation別の `render` に固定フレーズが残る。
- PR #171 `reader-value-draft.js`: 生活場面を先頭に置いたが、relation別の `compose` に固定文を持つ。特徴の読者価値を独立して導出・検証する機構ではない。実文4件の改善度は未認証。
- 以前の独立品質比較（`acquisition-20261111/independent-quality-review.json`）では、商品固有の特徴があっても購入場面や伝達力が弱いとの評価がある。
- 保存済み4商品の「候補あり」は**品質合格と別**。0/4合格の意味は認証未実施であり、品質不合格との確定ではない。

## 既存の購入判断知識の実測

`lib/product-decision-knowledge.js:getDecisionKnowledge` を保存済み4商品のローカル同定種別で照会：

- 収納ベンチ：`null`（種別別知識なし）。
- お掃除手袋：`null`（種別別知識なし）。
- モバイルバッテリー：知識あり。外出先での給電、容量/出力/端子/ケーブル内蔵等の選択軸があるが、個別の販売製品の選択理由は未証明。
- フライパン：知識あり。サイズ/素材/IH対応等の選択軸はあるが、「取っ手を外して重ねられる」特徴からの購入理由は現状の知識には明示されない。

したがって、カテゴリ知識が2/4にあることをもって、4商品の購入理由が理解できたとは判定しない。知識が存在しない種別に対し、文章テンプレートで欠落を隠さない。

## 原因の切り分け

| 段階 | 分かっていること | 足りないこと |
|---|---|---|
| 商品の同定 | 4件はローカルで商品種別を推定できる | セット・バリエーションの販売単位への所属証明 |
| 特徴抽出 | 原文に一致する特徴を4件で抽出できる | 商品名・箇条書き・否定条件の一般的な意味理解 |
| 購入理由 | 使用関係のラベルを付けている | 特徴→利用者の目的→選択する理由の**個別の意味関係** |
| 文章生成 | 書き出し・長さ・構成を変えた | 同一パターンから抜け、価値を過不足なく表現すること |
| 品質評価 | 旧出力保全、原文引用一致、テスト成功 | 未見商品・人による購買理由/自然さ/6軸独立評価 |

## 暫定採用判断

- PR #169 / #170 / #171 は**Draftの検証資産**として保持し、いずれも本番統合しない。
- これ以上、4商品向けのカテゴリ別導入文・言い換えルール・審査例外を追加しない。
- UI、本体生成、main、Production、認証、DB、決済、Groq実通信、過去の証拠を変更しない。
- 「テスト全件成功」と「魅力ある文章が完成」は別指標で報告する。

## 次に実装すべき最小単位

文章を直接出す前に、**購入理由の中間表現（buyer-decision plan）**を独立して評価する。必要条件：
1. 原文の**正確な引用・所属・条件**を明示する。
2. 「買い手の使用場面/目的」は商品説明の事実と混同せず、仮説として別フィールドにする。
3. 「その特徴が場面にどう関係するか」は、根拠があるときだけ列挙する。一般的な便利/快適/省スペースなどの推測は採用しない。
4. 商品と無関係な同じフレーズを繰り返さず、強い関係を一つ選び、残りは必要な補助/制約に限定する。
5. 中間表現に十分な関係がない場合は、魅力を作り話で補わず保留する。
6. まず4商品の**中間表現そのもの**を提示し、別商品で関係選択が再現するか確認する。中間表現が良くなるまではコピー生成器を変更しない。

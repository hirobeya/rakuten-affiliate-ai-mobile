前回の監査とPR #163の初回コミット `e889d47` を基準に、単発修正で止めず、全体経路との整合を確認した追記。過去の「CI失敗1件」は以下の修正後の結果で更新する。main / Production / 決済は変更しない。

## 一連の情報・操作経路

| 段階 | 現在の実装経路 | 次段階へ渡す条件・不変条件 |

| サーバー生成 | /api/room-copy→room-copy-handler→localZeroCall、未完成ならsemantic engine→機械検査・全文章AI検証 | product/sentences契約・既存検証を維持。草稿があることだけを理由にローカル完成とせず、不足時に検証へ回す |

## 残るCI失敗の根本と今回の解決

既存の780商品検査は「根拠のある草稿を作れた数112件以上」を求める。一方composeの入口で、商品名と引用可能な仕様があっても、場面・購入理由がない未知商品は文そのものを捨てていた。このため草稿生成91件となった。過去の単純なsource_label許可は撤回履歴があり、そのまま復活させない。

今回、正確な原文名称と仕様を保持した結果を明示的な `status:'draft'` として返す。既存 `status:'ok'` へ混ぜない。assessは従来どおりokと実際に本文へ選ばれた購入理由を必須にし、サーバーlocalZeroCallもok以外のstructured出力を完成扱いしない。appのlocalCopyAssessment、AI振り分け、最終コピー検査、各媒体の同一草稿経路を合わせて検査した。

商品名・商品ID別の例外、購入理由の捏造、テスト基準112の引下げはない。変更したブラウザ資産のURLも更新し、古いiPhoneセッションのキャッシュと区別できるようにした。

## 追加した接続検査

- `local-draft-boundaries.test.js`: 780件を実ブラウザ用モジュールとappの実際の判定関数へ通す。数値等の草稿が投稿可能にならず、サーバーが実際のlocalZeroCallを使ってAI確認へ進み、429なら1回で停止し草稿を返さないことを確認。
- `urenavi-workflow-integration.test.js`: 合成商品と模擬providerで実際のclient request→Preview handler→canonical検査→投稿準備→本人投稿確認→同商品URLの重複除外→交流のopen/complete→実績訂正→別端末復元→別アカウント隔離→検証済みcache再利用を接続。生成だけでは台帳に何も書かず、コピー準備だけではpostedにしないことも確認。
- 外部通信部分を模擬した接続検査であり、実楽天検索、実AI品質、実ROOM投稿、実機ブラウザ、実ログイン・DBの通し確認ではない。

## 完成に残るものと進める順序

1. 正規ログイン後PreviewとiPhoneの通し操作。現時点の実ブラウザ確認はログイン画面まで。Production側のログイン承認URLをPreview認証として再利用しない。起動時クラッシュの原因は端末ログ未取得のため未特定。
2. 無料検索と有料投稿文生成の境界。現searchは契約判定が必要。楽天の許諾と既存ユーザー・セッション保護を確認し、決済に触れずに設計を反映できる範囲を明確にする。
3. 許諾済み商品データでの未見カテゴリ品質・コピー採用率・待ち時間。780件中サーバーのローカル完成8件という低さが残り、タイトルだけで全商品を完成できるとはしない。
4. 実Groqの呼出数・入力/出力トークン・429・並列負荷。日次呼出制限と停止動作のテストだけでは契約固有の無料枠・多数利用者の処理量を保証しない。
5. 投稿済み・交流・成果・復元を実機で確認し、手動実績と正規成果データを突合。候補の省力発見、成果自動連携、クラウド同期は未完成。
6. 楽天商用供給許諾、ホスティング条件、価格・販売停止表示の整合、利用者試用と採算。一般販売や決済を開始しない。

CI成功だけを全体完成としない。各残課題にはコード検査・模擬検査・Preview実操作・iPhone実機・外部許諾のどの証拠が必要かを分けて記録する。

# 購入理由の共通判定と本文選択（2026-10-16 JST）

前提: PR #163 `4643069` の次工程。草稿と完成文の区別を維持し、画面とサーバーの品質差、根拠ある複数文の取りこぼしを調査した。main / Production / 決済、PR159/162の状態は変更しない。

## 確認した原因

- browser structured.assessは、衣類の半袖・長袖・季節、素材、洗える、充電式等の単独ラベルから作った一文にもreadyを返していた。server localZeroCallではこれらを購入理由不足として拒否していた。
- composeは購入理由候補を点数で選び、素材を選びたいという弱い文も本文へ並べた。サーバーでは弱い文の混入を理由に拒否するため、独立した根拠ある機能と素材を持つ商品も判定が噛み合わなかった。
- 場面文がない場合に複数の購入理由を一つの行へ結合していた。assessとAPIは理由が完全な一行として本文に存在することを検査するため、正しい文も見つからずAIへ振り分ける場合があった。

## 修正

1. サーバーで使用していた厳しい理由判定をstructured-room-copy.valueHasStrongReasonへ移し、browserの本文選択・readyとAPIのstructured経路で共有した。原文のfacts参照が必須。数値・寸法・枚数・素材、単独の袖・季節・洗える・充電式、品名の言い直しは、それだけでは強い理由にしない。
2. 強い理由を持つ文だけを本文の中心に選ぶ。弱い仕様は素材の導入・特徴欄等に保持し、独立した機能の存在を妨げない。商品別の例外や推測された便益は追加していない。
3. 選んだ購入理由をそれぞれ独立した行へ出力し、本文の完全一致検査が正しい文を検出できるようにした。
4. iPhoneの古い資産キャッシュと区別するためappの対象script URLを更新した。商品理解の他経路、semantic契約・検証、モデル・quota・429停止・再試行設定は変更していない。

## 商品説明付き17件を調べて判明した追加原因

同じ作業内で既存source_reviewed fixture17件も診断した。実商品を再取得したデータではない。

収納ベンチu02のitemCaption冒頭「Pickup Item!」には別商品の耐荷重150kg・折りたたみが含まれる。本商品の根拠は後半の約80kgで、実際の本体が折りたためるとは示されない。browser extractFactsはcaption全域で単語が見つかれば取り込むため、誤って「使わないときは折りたためます」をreadyとしていた。serverはこの商品を既に未完成としていた。

厳しい理由判定だけでは商品との紐付けを証明できないため、structuredのローカル完成には全採用factがitemName由来であることも共通条件とした。itemCaption/catchcopyからの単純な単語一致は草稿・診断には保持するが、ローカルの完成証明にはしない。導入の素材等も含め一つでも未確認の他ソースがあれば、ブラウザはコピー禁止・API確認へ進める。APIの別partner経路で商品と引用文を安全に紐付けられる場合や、既存semantic検証を通る場合まで禁止しない。タイトルで証明できる機能や前段のcaption-grounded洗濯ネット回帰は維持。

追加2テストで、既存の汚染実例、captionとcatchcopyの関連商品、補足素材の混入、evidence引数による迂回不可、タイトル単独の正例を確認。最新の全415テストは成功。ビルド相当の全Nodeコマンドも再実行した。

17件の診断ではサーバーlocal完成5件を維持し、browser readyは1件。u02の誤った折りたたみは拒否し、u09のcaption素材もローカルでは保留するが、サーバーはタイトルのIH対応から引き続き0 Groqで完成可能。追加API確認が常に追加Groq通信を意味するわけではない。実通信・実AIによる出典紐付け精度は未検証。

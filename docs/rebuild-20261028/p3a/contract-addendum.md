# P1-R：2026-10-28 の実行指示による限定追補

既存implementation-contract.mdの意味・安全性・4通信・モデル・上限を維持する。
以前の「P0成立までP2を停止」は、今回のユーザー承認により **DB非接続・実GroqなしのP2/P3-Aだけ解除**。本番運用成立判定は未合格。

- A=販売本体理解、B=特徴/所有者/適用範囲と選択意図の関係、C=全文生成、D=全文審査、E=一度の書き直し、F=全文再審査と完成判定。
- writer内部schemaはplan先行。sellingProduct、owners、features.scope、intentions、relations、bindings.clausesを保持。本文の全節を順序通り連結して本文と一致させる。
- 同一原文のUTF-16連続引用を保持し、外部sentences.quotesと内部binding引用を完全一致させる。審査による新しい引用の追加は不許可。
- 既存外部schemaを基準HEADから静的保存。DBへつながるprovider/handlerをimportせずに使用する。既存inspectとassessReviewを必ず呼ぶ。既存6品質軸に加えP1の独立6軸も全passが必要。
- 機械検査は参照・引用・全節対応・既存安全性の拒否専用。語一致で所有者/意味関係を確定しない。意味の正しさは原文全文と本文全文のAI審査責任。モックの肯定結果は意味理解の実証ではない。
- 意図・生成条件もhashとpayloadへ含む。版はschema/prompts/検査コード/既存安全性依存/engineから導出。既存runKeyによる抑止回避はない。
- 実験ディレクトリ全体の排他、原文キー単位の抑止、送信前のfsync永続化、全工程の予約、各payload再計算、既知usageの確認を行う。クラッシュのlockは自動解放しない。429/usage不明/保存不明は次の商品も停止。台帳破損も送信0。
- 容量は旧版と同じ透明な文字数ヒューリスティック。実トークナイザではなく、実消費/削減率/上限の保証にはしない。出力3000は予約上限で、実出力予測ではない。
- 全工程開始可能性の事前確認は、schema各欄最大文字数を使う保守的envelope。出力3000 tokensに同時に収まるかを無視して過大評価するため、運用容量の予測値にはしない。原文削除や検査省略で通さず容量不足で止める。現envelopeの過大さ自体を未解消事項として報告する。
- transportは注入関数のみ。実ネットワークadapter/本番ルートへの組込/環境変数によるキー読込は実装しない。P3-A起動器は秘密情報を引き継がず、Node通信入口と子プロセスを拒否する。

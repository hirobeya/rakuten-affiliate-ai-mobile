# スーパー・ウレナビ 基本設計（確定版）

この文書を、ウレナビの商品理解・AI利用・キャッシュ・コピー生成・検証・修正判断の最上位基準とする。

個別商品の場当たり修正ではなく、この設計に沿ってエンジン全体を改善する。

## 1. 目的

スーパー・ウレナビは、楽天商品を安全に理解し、Groq使用量を抑えながら、未知商品を含む幅広い商品で「買う理由が伝わる刺さる文章」を生成する。

同時に満たす成功条件は次のとおり。

1. 事実を捏造しない。
2. 商品の性能・効果・機能は、必ずその商品の原文根拠からのみ書く。
3. 悩み・使用場面は、個別商品ではなく商品タイプ単位の知識として再利用する。
4. Groqは必要な時だけ使う。
5. 一度得た理解・画像理解・タイプ知識は再利用する。
6. 未知商品にも一般化できる。
7. 安全性と刺さりを別軸で評価する。

## 2. 設計の核：推論を商品タイプ単位に移す

### 2.1 商品タイプ知識

悩み・使用場面は、個々の商品ではなく商品タイプの知識として持つ。

キーは正規化した `productType` とする。

Groqで商品タイプごとに原則1回だけ生成し、検証後にキャッシュする。同じタイプの全商品で再利用する。

商品タイプ知識には、以下のみを持たせる。

- 読み手が置かれやすい状況
- よくある悩み
- よくある使用場面
- 購入時に意識しやすい観点

商品タイプ知識には、商品の性能・効果・機能・優位性・具体仕様を一切書かない。

例：
- 許可：移動中に使う場面がある、収納場所を気にする人がいる、作業時間を短くしたい人がいる
- 禁止：長時間使える、静音、強力、速い、効果がある、○○機能で便利

### 2.2 タイプ知識の検証

生成した商品タイプ知識は、保存前に必ず検証する。

検証項目：
- 性能を断定していない
- 効果を断定していない
- 機能を追加していない
- 個別商品の仕様を含んでいない
- 特定ブランド・型番・商品名に依存していない
- 健康・美容・安全上の効果を推測していない

1つでも違反したら保存しない。

### 2.3 productType の条件

商品タイプ知識を使うのは、`productType` が検証済みで `valid=true` の場合だけとする。

不正・曖昧・未検証の productType にタイプ知識を結びつけない。

## 3. 商品の性能・メリットの原則

商品の性能・メリットは、その商品自身の原文に根拠がある事実からしか書かない。

文章構成は次の順序を基本とする。

1. 商品タイプ知識から得た悩み・使用場面
2. その商品で確認できた強い事実
3. その事実に直接紐づく生活メリット
4. 根拠となる具体仕様

重要：
商品タイプ知識は「読み手の状況」を補うために使うものであり、商品の性能説明を補完するためには使わない。

## 4. AIルーターの順序

処理順は固定する。

1. キャッシュ
2. ローカル
3. Groqテキスト
4. Groq画像

検索結果の一覧表示ではGroqを呼ばない。

Groqを呼ぶのは、ユーザーが投稿文の生成を押した時だけとする。

### 4.1 キャッシュ

最初に再利用可能な理解結果を確認する。

利用可能ならGroqを呼ばない。

### 4.2 ローカル

ローカルで「確定」としてよいのは、許可型の形で安全に判定できる場合だけとする。

推測・弱いヒューリスティック・曖昧一致を理由にGroqを省略しない。

ローカル確定の条件は、コードに商品名を直接書く方式ではなく、データ化された許可リスト・構造ルール・検証ルールで管理する。

### 4.3 Groqテキスト

キャッシュ・ローカルで productType を安全に確定できない場合に使う。

テキスト解析で productType が valid=true になった場合は、画像解析へ進まない。

### 4.4 Groq画像

Groq画像に進むのは、Groqテキスト解析後も `productType` が不正だった場合だけとする。

「特徴を増やしたい」「刺さる文章を作りたい」という理由だけで画像解析しない。

## 5. キャッシュ設計

キャッシュは3系統に分離する。

### 5.1 商品タイプ知識キャッシュ

キー：正規化した `productType`

保存：
- 悩み
- 使用場面
- 購入時の観点
- 生のGroq出力
- 生成時プロンプトバージョン（メタデータ）
- スキーマバージョン（メタデータ）
- 作成日時

読み出し時に最新ルールで再検証する。

### 5.2 商品理解キャッシュ

キー：
- `itemCode`
- 商品名と説明文の正規化ハッシュ

保存：
- Groqの生の出力
- productType候補
- features / sellingPoints の抽出結果
- 元データに対する根拠
- 使用したモデル
- プロンプトバージョン（メタデータ）
- スキーマバージョン（メタデータ）

### 5.3 画像理解キャッシュ

キー：正規化した画像URL

画像URLは、サイズ指定パラメータ（`?_ex=` 等）を除いて正規化する。

保存：
- 画像由来の生のGroq出力
- 画像から得た productType 補助情報
- 生成時メタデータ

同じ画像は再解析しない。

可能なら将来的に画像URLだけでなく画像指紋も併用できる設計にする。

### 5.4 バージョンをキャッシュキーに入れない

`PROMPT_VERSION` / `VALIDATION_RULE_VERSION` はキャッシュキーに入れない。

Groqの生の出力を保存し、読み出し時に最新の検証ルールで再検証する。

プロンプトバージョンはメタデータとして保存する。

再解析を判断するのは、原則としてスキーマ互換性がなくなった場合だけとする。

### 5.5 不明結果のキャッシュ

「解析したが不明」という結果は短期間だけネガティブキャッシュする。

目的は、同じ曖昧商品で短時間にGroqを連打しないこと。

429エラー・通信エラー・一時的なAPIエラーはキャッシュしない。

### 5.6 コピーはキャッシュしない

最終コピーはキャッシュしない。

商品理解・画像理解・商品タイプ知識を使って、毎回その時点の最新ロジックで生成する。

これにより、文章ロジックを改善してもGroq再解析を不要にする。

## 6. Unsupported benefit guard

原文にない機能・効果・用途を文章へ追加しない。

特に次を禁止する。

- 温度設定がある → 保温できる、と変換
- 軽い → 持ち運び用途の商品だと断定
- 防水記載なし → 水回りで使えると表現
- 美容カテゴリ → 美容効果を推測
- 健康カテゴリ → 健康改善を推測
- ノイズキャンセリング記載なし → 静かな環境になると表現
- 素材情報だけ → 耐久性が高いと断定

メリットは、必ず対応する事実を指し示せる状態で生成する。

## 7. 価値順位付け

商品の原文から確認できた事実だけを候補にする。

その上で、商品タイプ知識の「悩み・使用場面」と照合し、購入理由として重要な順に並べる。

重要：
固定キーワードだけで順位を決めない。

悪い例：
- 重量がある → 常に携帯性を最優先
- 温度がある → 常に温度訴求
- USBがある → 常に接続性を最優先

良い設計：
- タイプ知識が示す読み手の状況
- 商品に実際にある事実
- その事実から安全に導けるメリット

の3点を揃えて順位付けする。

## 8. メリット翻訳

文章化は次の関係を崩さない。

`悩み・場面 → 商品事実 → 生活メリット → 根拠仕様`

メリットは事実に1対1または明確な対応関係を持たせる。

原文に根拠のない購入後変化を作らない。

## 9. 書き出し多様化

専用の「書き出し多様化ロジック」は実装しない。

商品タイプ知識の悩み・使用場面と、商品ごとの強い事実の組み合わせにより自然に文章が変化する構造を採用する。

同一テンプレをランダムに言い換えるだけの仕組みは不要とする。

## 10. Groq使用量の計測

最初に計測ログを実装する。

最低限、投稿文生成1回ごとに経路を区別して記録する。

- cache
- local
- text
- image

将来的に以下も計測できる形を目指す。

- cache hit率
- local確定率
- Groqテキスト率
- Groq画像率
- 画像再解析回避数
- ネガティブキャッシュ命中数
- 429発生数

## 11. 実装順

実装順は次で固定する。

1. Groq使用量の計測ログ（cache / local / text / image）
2. キャッシュ分離と、バージョンをキーに入れない方式への変更
3. ルーター実装
   - ローカル確定でGroqを呼ばない
   - 商品理解キャッシュヒットでGroqを呼ばない
   - 画像キャッシュヒットでGroq画像を呼ばない
   - テキストで productType valid=true なら画像を呼ばない
4. Unsupported benefit guard
5. 商品タイプ知識キャッシュ
6. 価値順位付けとメリット翻訳
7. 固定780件による統合回帰と、本番での経路別実測

## 12. 実装ルール

### 12.1 個別商品パッチ禁止

ロジックに商品名や特定の商品だけを狙った語を直接書かない。

許可リスト・カテゴリ知識・商品タイプ正規化データはコードではなくデータファイルに置く。

### 12.2 PRの必須差分レポート

ロジック変更PRには、固定780件での変更前後の差分レポートを必ず添付する。

最低限含める：
- 生成件数
- fallback件数
- 商品タイプ変化数
- 仕様抽出変化数
- 意味変化・不正仕様・内部文言混入の差分
- 代表的な改善例
- 代表的な悪化例

悪化例がある場合は、原因説明なしでマージしない。

## 13. 評価方法

### 13.1 安全性評価

固定780件を中心に、少なくとも次を判定する。

- 適切
- 仕様と呼べない語
- 意味が変わる

安全性は自動回帰の主評価とする。

### 13.2 刺さり評価

固定30件を人が3段階で採点する。

- 刺さる
- 普通
- 刺さらない

安全性とは別に記録する。

刺さり評価では、少なくとも以下を見る。

- 1〜2文目で読み手の状況が想像できるか
- 買う理由が明確か
- 商品の強い事実が優先されているか
- 単なる仕様読み上げになっていないか
- 根拠を守りながら生活上のメリットが伝わるか

## 14. 完成条件

PASS件数だけで完成扱いしない。

スーパー・ウレナビの完成条件は、カテゴリ横断・未知商品を含む状態で継続的に以下を満たすこと。

- 正しい productType を取得できる
- 商品タイプ知識を安全に再利用できる
- 商品理解キャッシュを再利用できる
- 同一画像を再解析しない
- Groq使用量を必要最小限に抑える
- 原文根拠を守る
- 原文にない機能・効果・用途を足さない
- 買う理由が伝わる
- 固定780件で安全性が後退しない
- 固定30件で刺さりが改善する

この設計に反する短期的な個別修正は採用しない。
